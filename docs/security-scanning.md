# الفحص الأمني المستمر — MEEM STORE

## ما الذي يعمل تلقائيًا؟

يشغّل `.github/workflows/security.yml` عند كل Pull Request إلى `main` وعند أي Push إليها، ويمكن تشغيله يدويًا من GitHub Actions. يفحص:

- `npm audit` للاعتماديات.
- `CodeQL` لشيفرة JavaScript/TypeScript.
- `Gitleaks` للبحث عن أسرار في سجل Git (التعليقات ورفع تقرير الأسرار معطّلان).
- اختبارات المشروع الحالية: `npm test` و`npm run test:edge` و`npm run test:security`، ثم `lint` و`build` و`typecheck`.

اختبارات قاعدة البيانات الموجودة تعمل على PGlite محلي مع fixtures يتم التراجع عنها. هذه الفحوص لا تستخدم حسابات عملاء أو مفاتيح Supabase ولا تتصل بقاعدة الإنتاج. يجب التأكد من نتيجة تشغيل GitHub Actions قبل الاعتماد على أي PR.

## Strix: اختبارات اختراق موجهة

[Strix](https://github.com/usestrix/strix) يقبل مستودعًا وعنوان موقع، ويجري اختبارات تفاعلية ويعرض أدلة وخطوات إعادة الإنتاج. تشغيله المحلي يحتاج Docker ومفتاح LLM API؛ نسخته Cloud تستقبل الشيفرة والهدف في خدمة خارجية. لا يُشغَّل آليًا على المتجر المنشور أو على preview يستخدم قاعدة الإنتاج.

قبل تشغيله: أنشئ مشروع Supabase معزولًا ببيانات اختبار، اربط نسخة Vercel staging به، وجهز حسابين عاديين وحساب admin اختباريًا. استخدم حدودًا واضحة للطلبات واستبعد الدفع الحقيقي والرسائل الخارجية وعمليات حذف البيانات. تأكد من أن إعدادات الواجهة وEdge Functions في staging تشير حصريًا إلى قاعدة staging. بعدها يمكن تشغيل فحص white-box يدوي موجه إلى الشيفرة وstaging، ومراجعة كل finding وإعادة اختباره بعد الإصلاح. احتفظ بمفاتيح LLM وحسابات الاختبار داخل secret manager، ولا تضفها للمستودع.

لا يمكن اعتبار نتائج Strix أو CodeQL ضمانًا بعدم وجود ثغرات؛ يجب إثبات التأثير على هذا النظام والتحقق من الإصلاح ومن المسار الطبيعي.

## قاعدة البيانات والموقع

شغّل [Supabase Security Advisor](https://supabase.com/docs/guides/observability/advisors) على المشروع المعني، وافحص أذونات RLS و`SECURITY DEFINER` وStorage، ثم شغّل اختبارات عزل مستخدمين على staging فقط. قد يحذّر Advisor من دوال مقصود أن تكون متاحة؛ راجع فحص الصلاحيات داخل كل دالة قبل تعديل grants.

بعد تجهيز staging، شغّل [OWASP ZAP Baseline](https://www.zaproxy.org/docs/docker/baseline-scan/) على عنوان staging لالتقاط المشكلات الظاهرة في HTTP والصفحات. الاختبار المصادق عليه وتدفق الطلبات يحتاجان حسابات وبيانات وهمية؛ راجع صلاحيات فحص الـAPI وتأكد من rollback.

## Boosthis

[Boosthis](https://www.boosthis.com/help) أداة لمراقبة سرعة الصفحات وأخطاء التشغيل للمستخدمين الفعليين. يمكن تقييمها لاحقًا إذا أردنا قياسات أداء، لكنها لا تفحص RLS أو صلاحيات الدفع ولا تحل محل Strix أو اختبارات Supabase.

## آلية معالجة النتائج

لكل إنذار: تأكد من إمكانية إعادة الإنتاج ببيانات اختبار، حدد مسار الإدخال إلى قاعدة البيانات والأثر، أصلح السبب في فرع منفصل، شغّل الاختبارات الحالية، ثم أعد فحص الثغرة والمسار الطبيعي. لا تُنشَر تغييرات DB/Edge/frontend منفردة إذا كان بينها اعتماد متبادل.
